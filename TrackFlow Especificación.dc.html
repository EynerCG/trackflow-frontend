TrackFlow · Sprint 1

Frontend: especificación y decisiones de diseño

Septiembre 2026
Prototipo HTML

TrackFlow conecta cada punto de tu cadena logística en un solo lugar: registra el envío, reporta su paso por cada centro de distribución y consulta el estado en tiempo real con tu número de guía.

1. Contexto

Sistema de registro y seguimiento de envíos. El backend está construido, probado end-to-end y desplegado: Spring Boot, monolito modular con ingesta por eventos (RabbitMQ), PostgreSQL sobre Supabase en producción. Este documento cubre únicamente el frontend.

Sprint 1 cubre tres historias de usuario: HU-01 registrar un envío (remitente + destinatario), HU-02 registrar un evento logístico (un punto de la cadena reporta un movimiento), HU-03 consultar el estado actual de un envío.

2. Estado de la entrega

Prototipo funcional en un solo archivo, TrackFlow.dc.html, que consume la API real por red. No hay datos simulados: toda pantalla refleja lo que responde el backend, incluidos sus errores. La URL base es configurable; por defecto https://trackflow-5enb.onrender.com, y se cambia a http://localhost:8080 para desarrollo local (requiere docker compose up -d y ./mvnw spring-boot:run).

Toda petición tiene tiempo límite: 25 s para la consulta de rastreo (tolera el arranque en frío de Render), 6 s para el autocompletado de ciudad, 10 s el resto. Si se agota, la pantalla muestra el error de red con opción de reintentar, nunca un spinner infinito.

4. Sistema visual

Color

Azul marino #14305c como estructura: nav, hero, pie. Naranja #f4711a reservado a las acciones — un solo botón naranja por pantalla. Fondo de trabajo claro #f2f2f3 en las pantallas interiores. Sin color decorativo fuera de esos dos.

Tipografía

Barlow Condensed en títulos, Barlow en texto, 16 px de base. Los números de guía van con cifras tabulares y tracking amplio para que se lean como un código.

Forma

Esquinas rectas, marcos de línea fina con marcas de registro en las esquinas, retícula visible de celdas iguales. Las tarjetas no llevan relleno: son dibujos de línea. El botón primario es el único objeto sólido.

Badges de estado

Registrado gris · En centro de distribución azul · En tránsito azul · En reparto ámbar · Entregado verde.

5. Reglas transversales de la API

  • Las escrituras son asíncronas: siempre 202 Accepted, nunca 201. No hay confirmación instantánea de que el dato ya existe.
  • La ciudad es siempre un ciudadId numérico elegido por autocompletado, nunca texto libre.
  • tipoDocumento y numeroDocumento son campos separados, con validación por tipo.
  • No existe editar ni borrar: no hay PUT, PATCH ni DELETE. Corregir un error significa registrar un evento nuevo.
  • Las consultas son siempre públicas, con o sin protección activa en el backend.
  • Todo error 400 trae un detail legible; la UI lo muestra tal cual, sin reemplazarlo por texto genérico.

6. Contrato consumido

GET /api/ciudades?q={texto} — público

Hasta 10 coincidencias, primero las que empiezan por el texto. q vacío o ausente devuelve 400. Mismo catálogo para origen y destino.

POST /api/shipments — rol OPERADOR

Remitente y destinatario con el mismo shape (nombreCompleto, tipoDocumento, numeroDocumento, telefono, direccion, ciudadId) más descripcion. Todos los campos obligatorios. Responde 202 con trackingNumber, eventId, destinatario, ciudad de destino, solicitadoEn y estadoProcesamiento.

El trackingNumber lo genera el backend: el formulario no tiene campo de guía, es puro output, y es definitivo desde la respuesta aunque el registro siga procesándose. La UI muestra "procesando" y reintenta GET /api/tracking/{tn} cada 300 ms unos segundos para confirmar.

TipoFormato del número de documento
CC, CE6 a 10 dígitos
TI10 a 11 dígitos
PP5 a 15 caracteres, letras mayúsculas y dígitos
NIT9 a 10 dígitos; opcionalmente con dígito de verificación (890903938-8), validado contra las ponderaciones de la DIAN

El formato esperado se muestra dinámicamente bajo el campo según el tipo elegido. Los errores 400 llegan en formato ProblemDetail y, con campos faltantes, traen además camposFaltantes; la UI lista ambos.

POST /api/shipments/{trackingNumber}/events — rol OPERADOR

Tipos: RECEIVED_AT_CENTER, DISPATCHED, ARRIVED_AT_DESTINATION_CENTER, OUT_FOR_DELIVERY, DELIVERED. punto obligatorio, observaciones opcional, ocurridoEn opcional.

Si no se envía ocurridoEn se asume que el movimiento acaba de ocurrir; el campo se diseñó opcional con "ahora" por defecto y ayuda explícita para reportes tardíos. Una fecha futura devuelve 400. Guía inexistente devuelve 404. Un evento con fecha anterior al último aplicado se guarda en el historial pero no cambia el estado visible del envío: la línea de tiempo lo marca como reporte rezagado.

GET /api/tracking/{trackingNumber} — público

Estado actual, ciudad de destino, fecha de registro, si tiene movimientos, último punto y último movimiento. Guía inexistente devuelve 404, que la UI presenta como un estado amable y explícito, no como error crudo: "No encontramos ningún envío con ese número. Verifica que esté bien escrito", con el código de respuesta a la vista para diagnóstico.

GET /api/shipments/{trackingNumber}/events — público

Historial completo ordenado por fecha real de ocurrencia, no por orden de llegada. Se renderiza como línea de tiempo vertical con ícono por tipo de evento.

POST /api/auth/login — público

Un solo formulario, sin selector de rol: el backend decide según las credenciales y el admin siempre incluye los permisos de operador ("ADMIN OPERADOR"). El JWT se guarda y se envía como Authorization: Bearer {token} en los POST protegidos. Credenciales incorrectas devuelven 401. Si el entorno no tiene credenciales configuradas devuelve 503 y se muestra el mensaje específico "No hay credenciales configuradas en este entorno", no un error genérico de usuario o clave. El claim de roles decide qué se muestra en la UI de operador, nunca antes del login.

POST /api/admin/reconstruir-proyecciones — rol ADMIN

Sin body. Devuelve el conteo de envíos y eventos republicados. Pantalla simple, visible solo con rol ADMIN.

7. Estados diseñados

Cada pantalla cubre el camino completo, no solo el feliz: cargando, vacío (envío sin movimientos), error de red con reintento, 404 explícito, validación de formato en cliente antes de llamar al backend, 400 con el detail del backend y su lista de campos faltantes, 401/403 con invitación a iniciar sesión, 503 sin credenciales, y éxito 202 con aviso de procesamiento asíncrono.

9. Implementación prevista

Next.js 16 con App Router, React 19 y TypeScript; Tailwind CSS v4 con shadcn/ui estilo base-nova; primitivas Radix vía @base-ui/react, lucide-react para íconos y axios para HTTP. Faltan por crear los componentes label, textarea, table, dialog, tabs, notificación y el combobox de autocompletado, que se arma con popover más input y lista filtrada. Este prototipo es la referencia visual y de comportamiento para esa implementación.
